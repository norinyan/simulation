## 1. 目标与范围

将项目整理为 `sim_bringup`、`planning`、`control`、`hmi` 四个包，分开环境、规划、运动执行和人机交互。删除专用测试与验收代码，消除重复逻辑，保留算法替换能力，再解决轮式停走、动态等待和足式计算耗时。

保留原两级台阶 A→B、三层楼现有9个点及任意不同点对选择、三维全局规划、轮足局部规划、平台足式转向、行人、观察视角和落脚点显示。是否同层、经过几次楼梯，由全局路径决定，不由HMI按高度或点对白名单决定。

采用理想运动执行，不研究动力学、接触力或真实控制算法。不新增算法、电梯、感知、core包、独立评测平台或通用插件框架。不修改World几何、机器人机构、预设点位及行人路线来通过验收。

当前已知问题：F2-ROOM→F2-EAST曾因行人冲突预测持续等待而超时。统一严格停车精度可能影响内部转角和预测，原因尚需局部对照。重构与修复分别记录，不能将结构整理等同于导航问题解决。

## 2. 职责与启动入口

| 包 | 职责 | 启动方式 |
|---|---|---|
| sim_bringup | Gazebo、World、统一地图、行人和场景可视化 | ros2 launch sim_bringup scene.launch.py |
| planning | 算法接口、A*／TEB／足式实现、导航调度 | ros2 launch planning planning.launch.py |
| control | 指定点生成机器人、理想执行、轮足变换、反馈及执行保护 | ros2 launch control control.launch.py |
| hmi | 场景／规划／控制三个界面块、启动协调与状态显示 | ros2 run hmi panel |

只有三个业务launch，不保留 `simulation.launch.py` 和HMI launch。三个launch可独立组合使用，不依赖HMI才能完成导航；通过真实就绪状态衔接，不靠固定延时。

- **HMI协调器**：复用现有会话管理，组织启动、用户请求、配置冻结和退出；不决定路线或轮足模式。
- **导航调度器**：按全局路段组织局部规划，请求模式切换，依据实际反馈推进、等待或失败；不直接追踪机器人。
- **控制执行端**：消费局部轨迹，完成跟随、停稳和模式变换；不选择路线或重新规划。保留Gazebo执行插件，不为拆包强行增加控制节点。

## 3. 配置与通信边界

### 配置

| 配置 | 内容与归属 |
|---|---|
| planning/config/planning.yaml | 三类算法及参数、共同规划运动约束、计算预算、重规划与导航策略 |
| sim_bringup/config/scene.yaml | 场景及World路径、机器人几何与物理能力、仿真参数、障碍物配置、预设点位、robot.execution执行参数 |

World是真实静态几何来源，不在scene.yaml重复维护墙、家具、楼梯坐标。机器人尺寸和物理限位只保留一份定义，URDF与规划读取同源配置；规划采用的运动约束不得超出物理能力。

planning和control由launch参数接收同一份scene_file路径及场景选择，由HMI或命令行提供；不得为查找配置而反向依赖sim_bringup的启动代码。

出生点预设由原presets.yaml归入scene.yaml，HMI读取同一份。起终点、算法组合是运行时任务请求，不改写源配置。每个任务接收后冻结请求；换场景重建地图，普通换任务不重读World。

内部转角、模式边界与最终目标的停车要求明确区分；执行参数归robot.execution，通行预测使用相同规则，不另藏一组阈值。具体数值及调整效果在第三阶段验证。

### 通信

| 数据或操作 | 通道 | 最低约定 |
|---|---|---|
| 统一地图 | sim_bringup→planning Topic | Reliable、Transient Local、保留最新一份；发布端随场景存活，支持规划晚启动 |
| 行人状态 | sim_bringup→planning Topic | 身份、时间、位姿及运动状态；不烘焙进静态地图 |
| 局部轨迹、模式请求 | planning→control Topic | Reliable、Volatile；任务及路段标识、时间、坐标系、有效期；拒绝旧任务和过期命令，不重放历史运动指令 |
| 实际状态、执行结果 | control→planning／hmi Topic | 位姿、速度、双足及支撑、模式、就绪／完成／失败 |
| 开始、停止 | HMI→后端 Service | 响应只表示接受或拒绝；实际进度与终态由Topic反馈 |
| 算法选择 | 参数或任务请求 | 三类独立选择，忙时冻结，未知名称明确拒绝 |

统一地图包含场景标识／版本、坐标系、静态实体、分层支撑区域、双向楼梯连接及踏面／平台。规划收到完整匹配地图后持有内存，不为每次任务重复解析World。

优先复用现有标准消息。结构化地图及必要任务协议的最少自定义消息放在planning包内的msg／srv目录，不另建第五个接口包。sim_bringup和control可依赖planning的公共类型／消息／基础运动库；planning不得反向依赖这两个包，控制端不链接具体规划算法。消息传输类型与算法C++类型分开适配。

公共基础库只承载类型、几何和运动数学，不链接具体算法；算法选择入口可以依赖具体算法库，避免构建目标循环依赖。

轮式输出带时间的运动轨迹，足式输出落脚序列及机身／双足轨迹，保留各自表达。控制端负责追踪和终端停稳，规划节点不得再保留另一套追踪控制。共享插值、运动学及轮式运动规则，预测不能复制一套近似执行逻辑。轮式滚动规划与执行保持异步，以同一仿真时钟和实际状态衔接；不按每个预测窗口强制停车，也不跳到延迟轨迹的起点。

## 5. 分阶段实施

每阶段交付实际改动、必要验证和未完成项后停止，用户确认再进入下一阶段。

| 阶段 | 工作 | 验收边界 |
|---|---|---|
| 1：迁移与纯减法 | 建立四包三入口、迁移配置与机器人资源、删除专用测试验收及构建耦合 | 从干净工作区构建；三个launch和HMI入口可用；场景、行人及机器人资源可加载；原两级台阶A→B可运行。不同时调速度或停车策略 |
| 2：职责与通信贯通 | 统一地图Topic、规划与执行分离、导航调度与HMI协调器、公共能力解耦 | 规划晚启动能收到地图；同进程换任务不重解析World；同层及代表上／下楼可规划执行；开始／停止、模式就绪和失败反馈闭环；未知算法拒绝，忙时配置冻结 |
| 3：修复与提速 | 先局部验证停车精度与通道预测，再优化轮式停走及足式计算 | 既有失败路线恢复通行；代表路线实际到达；轮足计算与运动时长分别报告；无法满足时停相关尝试并讨论，不改标准硬过 |

阶段1只做必要的包名、资源路径、配置和启动适配，旧算法与执行逻辑先保持；规划／执行职责及Topic协议的完整迁移在阶段2完成。每阶段必须可构建、可运行，不交付依赖下一阶段才能启动的中间版本。

第三阶段先减少重复计算、无关障碍遍历、不必要停转与保守等待，再考虑其他优化。保留已实现的自适应步时，不引入名义足式预求解或动作库。默认保持原速度／加速度／关节限制，提高限速另行确认。

## 6. 验收与成本控制

删除专用验收代码不等于不确认功能。使用正常launch、HMI及现有运行接口做必要检查，不另造批量验收框架。按用户要求，取消截图取证、GUI人工确认及视角切换的专门验收；保留现有可视化功能，不以截图作为阶段交付条件。

最终代表路线：原两级台阶A→B；F1-ENTRY→F1-ROOM；F1-STAIR↔F2-STAIR；F1-ROOM→F3-WINDOW；F3-EAST→F1-ENTRY；F2-ROOM→F2-EAST。覆盖原任务、同层、双向楼梯、连续跨两层及已知动态失败。三层9点任意不同点对选择仍是功能目标，本轮不要求72条逐条实跑，也不宣称未执行点对已验证通过。

实际完成同时满足：DONE、位置误差≤5cm、朝向误差≤5°、目标机身高度误差≤1cm，最终实际线／角速度绝对值<0.001。楼梯及中间平台全程足式，支撑脚不穿地、不滑动、不瞬移；模式切换在有空间的平地停稳后进行。原World行人与碰撞保持，等待超时、保护停车和服务请求成功均不算到达。

正常任务名义完整足式预求解为0、实际足式入口求解一次、默认密集独立复查为0。时间戳、任务标识和取消贯穿接口，停止后旧结果不得执行；足式停止保留安全姿态，不自动收腿或续跑。

优先5倍加速，10倍仅在反馈与执行稳定时使用。计算耗时、仿真运动时间、墙钟时间和实际倍率分别记录。改动受影响的任务才重跑，最终代表任务在相关行为定版后集中验收；不在每次搬文件后重跑整套任务。新的失败先用最小局部实验定位，成本明显增加或需要改变主要方案、约束和验收标准时先讨论。

旧阶段过程不再作为实施要求。原build／install／log／results已按用户要求删除，旧验收原始证据不再可复查；doc图片与源码保留。后续结果如实区分规划成功、实际到达、失败和未执行，不引用已删除证据证明新版本通过。
